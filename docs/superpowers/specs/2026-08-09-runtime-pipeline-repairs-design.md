# 运行链路修复设计

## 目标

在不修改交易阈值、仓位算法和策略收益逻辑的前提下，恢复四条原生链路：新闻采集结果进入新闻策略、体育策略进入检测调度、加密系列配置在跨进程启动后可被交易运行时读取、shadow 成交写入并展示在模拟账本。

## 已确认的故障链

1. 新闻数据源返回的是本次抓取记录，但 `NewsFeedService` 用文章发布时间 `observed_at` 与本轮开始时间比较，历史发布而刚抓取的文章被全部丢弃。
2. 体育策略声明 `source_key="sports"`，检测进程只加载 `scanner`，扫描器又只接受 `scanner`，因此策略没有进入 `market_data_refresh` 调度。
3. 加密系列 ID 保存在 `AppSettings`。交易进程早于首次设置行创建时启动，会把空配置常驻内存；当前运行时没有针对“系列全空”的低频恢复读取。
4. shadow 回填以 `commit=False` 写模拟账本，只执行 `flush`。空闲周期的心跳 UPDATE 可能没有行变更，因而不会提交，关闭 session 后回滚。前端兜底又只接受 `paper`，而后端订单模式为 `shadow`。
5. 原生 `btc_eth_directional_edge` 引用了官方 ML 能力模块，但策略加载器的应用模块白名单遗漏 `services.ml`，导致该策略校验失败。

## 最小修改

- 新闻：用 `ingested_at` 判断记录是否属于本轮抓取；保留文章发布时间 `observed_at` 作为业务时间，不再混用两种时间语义。
- 体育：检测进程加载 `scanner` 与 `sports`；扫描器的市场刷新分区明确接收这两个 source key，不改变体育策略自身语义。
- 加密：市场运行时每 10 秒节流读取一次 `AppSettings` 中的搜索/加密配置，随后走原有 `CryptoService` 获取和缓存逻辑；避免每秒扫描都访问数据库，同时保证首次懒创建和后续设置修改可以生效。
- ML 导入：只把项目自带的 `services.ml` 加入策略导入白名单，不扩大到整个 `services` 命名空间。
- 模拟账本：shadow 回填成功后由该语义单元负责提交，确保订单上的 `simulation_ledger` 与同一事务中的模拟账户、成交和持仓一起落库。
- 前端：兜底持仓使用数据库迁移后唯一有效的模拟模式 `shadow`；模拟账本已有持仓仍优先，避免重复显示。

## 非目标

- 不放宽点差、流动性、WS 新鲜度、叠仓或风控门槛。
- 不制造模拟订单或伪造收益。
- 不启用实盘凭据，不修改 live 权限。
- 不重构扫描器、策略框架或账户页面。

## 风险与回滚

- 新闻量会恢复，去重仍由现有文章 ID/upsert 负责；如出现异常可单独回滚新闻过滤变更。
- 体育策略会真实参与扫描，但仍受原策略和质量门槛约束；零机会不等于链路失败。
- 加密恢复读取只在配置全空时发生，避免每秒扫描造成 DB 压力。
- 回填提交会提交该 session 在回填前的待处理变更；调用点此前只有读取，后续写入仍属于同一维护周期。回归测试必须跨 session 验证持久化。

## 验收证据

- 原代码上的新增回归测试先失败，修改后通过。
- 后端聚焦测试、前端 TypeScript/Vite 构建通过。
- 固定本地源码重新构建并重启，不使用上游 `latest` 镜像。
- 运行态检查 worker 日志、数据库计数和 API：新闻有输入记录，体育策略已加载并被调度，加密 market_count 非零，shadow 回填后 simulation trade/position 可查询。
- 是否成交仍由原策略门槛决定；必须分别报告“链路正常但无信号”和“链路故障”。
