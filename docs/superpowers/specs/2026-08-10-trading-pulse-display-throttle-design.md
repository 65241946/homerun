# 机器人活动流前端降频设计

## 1. 目标

解决机器人页面打开后因高频活动流更新导致浏览器和整台电脑卡顿的问题，同时保证后台市场采集、策略计算、模拟交易、订单处理、数据库记录和日志输出继续按原频率运行。

采用方案 A：普通扫描、决策和事件只在前端每 30 秒批量展示一次；新订单和严重风险事件仍即时展示，但不使用闪烁动画；用户可以手动立即刷新。

## 2. 已确认事实

- `App.tsx` 通过 `useWebSocket('/ws')` 接收 WebSocket 消息；`useWebSocket.ts` 当前对每条允许的消息执行一次 React `setLastMessage`。
- `useRealtimeInvalidation.ts` 当前收到每条 `trader_decision` 和 `trader_event` 后立即写入 React Query 缓存，并以 120 毫秒窗口安排相关查询失效。
- `TradingPanel.tsx` 会把决策、订单和事件重新合并、去重、排序为活动流；上游缓存每次变化都会触发这条计算链。
- 当前“暂停”只冻结最终显示列表，WebSocket 状态更新、查询缓存写入和上游活动流重算仍在继续，因此不能从根源消除卡顿。
- 当前主界面仅在机器人页面激活时订阅 `trading` 频道，离开页面后 `TradingPanel` 会卸载；该边界可以用于停止活动流展示批次。
- 运行态样本在约 552 秒内产生 1,000 条决策，约为 1.81 条/秒。该频率足以造成持续的 React 更新，但不应因此降低后台处理频率。

## 3. 修改边界

本次只修改前端消息发布、查询缓存批量更新和机器人活动流显示。

明确不修改：

- WebSocket 服务端、工作器、扫描周期和策略运行周期；
- 机会、信号、决策、订单和事件的数据库写入；
- 模拟或实盘的下单、成交、持仓、余额、PnL、费用和结算逻辑；
- 任何策略源码、参数、阈值、风险限制或账户配置；
- 后端 API 返回结构和日志持久化频率。

前端延迟展示不等于后台延迟执行。订单时间、成交时间和策略判断时间仍以后台记录为准。

## 4. 消息分级

### 4.1 30 秒批量展示

以下高频且不要求操作员逐条即时响应的 WebSocket 消息不再进入 React state：

- `trader_decision`；
- 严重级别以下的 `trader_event`。

机器人页复用项目现有的决策和事件只读查询，每 30 秒从后台数据库获取一次完整快照。这样数据库仍是界面日志的事实源，也不会同时存在“WebSocket 缓冲写缓存”和“API 回填”两条重复更新链。

### 4.2 即时展示

以下消息继续即时进入前端状态：

- `trader_order`，包括新订单及订单状态变化；
- `trader_event` 中严重级别为 `warning`、`warn`、`error`、`critical` 或 `failed` 的风险/故障事件；
- 与后台通知安全边界一致的 `kill_switch`、`live_preflight` 事件。

即时事件只更新必要的订单、风险和总览缓存，不触发普通活动查询的额外刷新。即时行不使用 `animate-pulse` 或其他持续闪烁效果。

其他非交易高频消息保持现有行为，本次不扩大改动范围。

## 5. 前端数据流设计

### 5.1 WebSocket 接收与 React 发布分离

浏览器仍逐条接收服务器消息，但主 `App` 调用方对普通交易活动不调用 React state setter。其他 WebSocket 消息及其他调用方保持现有行为。

机器人活动展示使用两条更新路径：

1. 即时消息保持现有单消息路径；
2. 普通交易活动由现有只读 API 每 30 秒返回一次数据库快照。

不新增第二套前端消息缓冲器。该选择复用项目已经存在的 `allDecisionsQuery`、`allEventsQuery` 和 firehose 查询，避免重复缓存、计时器、去重规则和覆盖顺序成为新的交易诊断风险。

### 5.2 页面生命周期

- 机器人页面未激活时，`TradingPanel` 保持卸载，普通交易活动的 WebSocket 副本不进入 React。
- 浏览器页面不可见时，沿用 React Query 的后台暂停行为，不执行活动流渲染。
- 重新进入机器人页面或重新获得焦点时，从现有只读 API 重新获取决策、事件和活动流快照一次，再恢复 30 秒查询周期。
- 这些行为只影响界面展示缓存，不删除数据库或后端日志。

### 5.3 手动立即刷新

活动流控制区增加“立即刷新”按钮。点击后：

1. 重新请求决策、事件、活动流和订单只读接口；
2. 不触发后台扫描、策略执行、下单或账户变更。

按钮执行期间防止重复点击，并显示最后一次界面刷新时间。

### 5.4 界面语义

- 将“实时脉冲流”改为“最近活动（30 秒刷新）”，避免把批量展示误解为逐条实时执行。
- 保留暂停功能，但文案明确为“暂停界面更新”；暂停不影响后台。
- 删除活动行的持续闪烁动画；订单和严重风险信息通过固定颜色、图标和时间显示优先级。
- 活动列表继续使用现有行数上限和虚拟/截断显示方式，不增加默认展示量。

## 6. 测试设计

先写失败测试，再写实现。

### 6.1 消息分级单元测试

验证：

1. 普通决策和普通事件不会发布到主 React 消息状态；
2. 订单、`warn`、`warning`、`error`、`critical`、`kill_switch` 和 `live_preflight` 保持即时；
3. 不启用降频选项的其他 WebSocket 调用方保持原行为；
4. 机器人页的决策、事件和活动流查询周期为 30 秒；
5. 重新进入页面只重新拉取一次快照；
6. 手动立即刷新只调用现有 GET queryFn。

### 6.2 组件测试

- 30 秒到达前活动列表不因普通 WebSocket 消息逐条变化，查询完成后显示后台快照；
- “立即刷新”能够提前获取后台快照；
- 标题和暂停文案准确说明仅影响界面；
- 订单和严重风险行立即出现且没有闪烁 class；
- 页面切换后不存在残留定时器或卸载组件更新警告。

### 6.3 回归验证

- 运行前端类型检查、构建和基于现有 `vite-node` 的聚焦测试；
- 在同一观察窗口对比前后端：后台决策/事件记录持续增长，前端普通活动最多每 30 秒更新一次；
- 核对修改前后的订单、持仓、余额、PnL 和策略配置，确认没有因前端降频发生语义变化；
- 使用浏览器性能面板确认机器人页面的 React 提交频率和主线程占用明显下降。

## 7. 验收标准

- 后台扫描、策略、订单和数据库写入频率没有改变；
- 普通决策/事件的界面更新频率不高于每 30 秒一次；
- 新订单和严重风险事件在 WebSocket 到达后 1 秒内显示；
- 普通活动以后台只读 API 返回的现有窗口和上限为准，展示延迟不超过 30 秒；
- 离开机器人页面后不再因交易活动流产生持续 React 渲染；
- 手动刷新不会触发任何交易副作用；
- 页面保持可操作，鼠标和滚动不再因活动流持续更新而明显卡顿。

## 8. 风险与回滚

主要风险是错误分级导致重要消息被延迟。通过与后台 notifier 的严重级别和事件类型保持一致、即时事件测试及 API 快照复核控制风险。

若验收异常，只回滚前端 WebSocket 展示过滤、活动查询周期和活动流文案；后端、数据库、策略和交易账本无需迁移或恢复。
