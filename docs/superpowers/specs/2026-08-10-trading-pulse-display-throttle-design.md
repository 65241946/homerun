# 机器人活动流前端降频设计

## 1. 目标

解决机器人页面打开后因高频活动流更新导致浏览器和整台电脑卡顿的问题，同时保证后台市场采集、策略计算、模拟交易、订单处理、数据库记录和日志输出继续按原频率运行。

采用方案 A：普通扫描、决策和事件只在前端每 30 秒批量展示一次；新订单和严重风险事件仍即时展示，但不使用闪烁动画；用户可以手动立即刷新。

## 2. 已确认事实

- `App.tsx` 通过 `useWebSocket('/ws')` 接收 WebSocket 消息；`useWebSocket.ts` 当前对每条允许的消息执行一次 React `setLastMessage`。
- `useRealtimeInvalidation.ts` 当前收到每条 `trader_decision` 和 `trader_event` 后立即写入 React Query 缓存，并以 120 毫秒窗口安排相关查询失效。
- `TradingPanel.tsx` 会把决策、订单和事件重新合并、去重、排序为活动流；上游缓存每次变化都会触发这条计算链。
- 当前“暂停”只冻结最终显示列表，WebSocket 状态更新、查询缓存写入和上游活动流重算仍在继续，因此不能从根源消除卡顿。
- 当前主界面仅在机器人页面激活时订阅 `trading` 频道，离开页面后 `TradingPanel` 会卸载；该边界可以用于停止活动流展示批次。
- 运行态样本在约 552 秒内产生 1,000 条决策，约为 1.81 条/秒。该频率足以造成持续的 React 更新，但不应因此降低后台处理频率。

## 3. 修改边界

本次只修改前端消息发布、查询缓存批量更新和机器人活动流显示。

明确不修改：

- WebSocket 服务端、工作器、扫描周期和策略运行周期；
- 机会、信号、决策、订单和事件的数据库写入；
- 模拟或实盘的下单、成交、持仓、余额、PnL、费用和结算逻辑；
- 任何策略源码、参数、阈值、风险限制或账户配置；
- 后端 API 返回结构和日志持久化频率。

前端延迟展示不等于后台延迟执行。订单时间、成交时间和策略判断时间仍以后台记录为准。

## 4. 消息分级

### 4.1 30 秒批量展示

以下高频且不要求操作员逐条即时响应的消息进入前端有界缓冲区：

- `trader_decision`；
- 严重级别以下的 `trader_event`。

缓冲区按消息 ID 去重，并沿用现有活动数据上限，防止页面长时间打开后内存持续增长。每 30 秒只执行一次批量缓存合并；同一批次对同一个 React Query 缓存键最多写入一次，不能逐条回放造成新的渲染风暴。

### 4.2 即时展示

以下消息继续即时进入前端状态：

- `trader_order`，包括新订单及订单状态变化；
- `trader_event` 中严重级别为 `warning`、`warn`、`error` 或 `failed` 的风险/故障事件。

即时事件只更新必要的订单、风险和总览缓存，不触发普通活动消息的提前整批回放。即时行不使用 `animate-pulse` 或其他持续闪烁效果。

其他非交易高频消息保持现有行为，本次不扩大改动范围。

## 5. 前端数据流设计

### 5.1 WebSocket 接收与 React 发布分离

浏览器仍逐条接收服务器消息，但普通交易活动先写入 `ref` 持有的有界缓冲区，不对每条消息调用 React state setter。

主 WebSocket hook 为当前调用方提供两条发布路径：

1. 即时消息保持现有单消息路径；
2. 普通交易活动以数组形式每 30 秒发布一次。

批量路径必须保留批次内全部去重后的消息，不能只保留“最后一条”，否则会让界面日志缺失。`useRealtimeInvalidation` 对一批消息按类型归并后，一次性合并到对应缓存。

### 5.2 页面生命周期

- 机器人页面未激活或浏览器页面不可见时，不执行普通活动流的定时 React 发布。
- 离开机器人页面时清空仅用于展示的待发布缓冲区，避免返回时回放过期的大量 UI 消息。
- 重新进入机器人页面时，从现有只读 API 重新获取决策、事件和活动流快照一次，再开始新的 30 秒批次。
- 这些行为只影响界面展示缓存，不删除数据库或后端日志。

### 5.3 手动立即刷新

活动流控制区增加“立即刷新”按钮。点击后：

1. 合并当前前端待展示批次；
2. 重新请求决策、事件和活动流只读接口；
3. 不触发后台扫描、策略执行、下单或账户变更。

按钮执行期间防止重复点击，并显示最后一次界面刷新时间。

### 5.4 界面语义

- 将“实时脉冲流”改为“最近活动（30 秒刷新）”，避免把批量展示误解为逐条实时执行。
- 保留暂停功能，但文案明确为“暂停界面更新”；暂停不影响后台。
- 删除活动行的持续闪烁动画；订单和严重风险信息通过固定颜色、图标和时间显示优先级。
- 活动列表继续使用现有行数上限和虚拟/截断显示方式，不增加默认展示量。

## 6. 测试设计

先写失败测试，再写实现。

### 6.1 消息批处理单元测试

使用假定时器验证：

1. 30 秒内连续收到 100 条普通决策时，不发生逐条 React 发布或逐条查询缓存写入；
2. 到达 30 秒时只发布一个批次，并且每个目标缓存键只更新一次；
3. 相同 ID 的消息只保留最新版本，缓冲区不会超过既定上限；
4. 普通事件进入批次，订单和严重风险事件立即发布；
5. 即时事件不会提前回放普通批次；
6. 页面离开、隐藏和组件卸载时定时器正确清理；
7. 重新进入页面只重新拉取一次快照，不回放离开期间的展示缓冲；
8. 手动立即刷新会合并当前批次并重新拉取只读数据。

### 6.2 组件测试

- 30 秒到达前活动列表不因普通消息逐条变化，到时只更新一次；
- “立即刷新”能够提前显示已缓冲数据；
- 标题和暂停文案准确说明仅影响界面；
- 订单和严重风险行立即出现且没有闪烁 class；
- 页面切换后不存在残留定时器或卸载组件更新警告。

### 6.3 回归验证

- 运行前端类型检查、构建和相关 Vitest；
- 在同一观察窗口对比前后端：后台决策/事件记录持续增长，前端普通活动最多每 30 秒更新一次；
- 核对修改前后的订单、持仓、余额、PnL 和策略配置，确认没有因前端降频发生语义变化；
- 使用浏览器性能面板确认机器人页面的 React 提交频率和主线程占用明显下降。

## 7. 验收标准

- 后台扫描、策略、订单和数据库写入频率没有改变；
- 普通决策/事件的界面更新频率不高于每 30 秒一次；
- 新订单和严重风险事件在 WebSocket 到达后 1 秒内显示；
- 普通消息在页面持续打开时不丢失当前批次内的唯一记录，展示延迟不超过 30 秒；
- 离开机器人页面后不再因交易活动流产生持续 React 渲染；
- 手动刷新不会触发任何交易副作用；
- 页面保持可操作，鼠标和滚动不再因活动流持续更新而明显卡顿。

## 8. 风险与回滚

主要风险是错误分级导致重要消息被延迟，或批量合并时丢失日志。通过明确白名单、批次完整性测试、严重事件即时测试和 API 快照复核控制风险。

若验收异常，只回滚前端 WebSocket 批量发布、查询缓存批量合并和活动流文案；后端、数据库、策略和交易账本无需迁移或恢复。
