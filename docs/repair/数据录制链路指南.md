# Homerun 数据录制链路:核查、加固与回测就绪指南

依据:对仓库录制面代码的逐行调查(引用均为真实 file:line,HEAD `dbf0c5c3`)。目标:确认你本机"正在收集的数据"到底录了什么、把留存加固到能支撑回测/walk-forward,并列出会静默毁掉回测数据的坑。

## 1. 录制面的真实架构(你系统里已有的,不用新建)

数据流:`RecordingFeedManager`(独立 Polymarket WS 连接池,`services/recording_feed.py:185-203`)→ `LiveMarketDataIngestor`(校验、切 delta、快照节流 0.5s/token,`services/market_data_ingestor.py`)→ `BookParquetSink`(15 分钟窗口,zstd parquet,2s flush、30s 压实、60s 注册目录到 `provider_datasets`,`services/external_data/book_parquet_sink.py`)。

- **录什么**:`snapshots`(L2 双边 25 档 + best bid/ask + spread + 成交带)与 `deltas`(逐档 trade/cancel 事件,含队列深度),schema 在 `parquet_schema.py:52-91`。**SQL 里已无 book 表**(迁移 `202605290001` 删除),parquet 是唯一 L2 载体。
- **存哪**:默认 `<repo>/data/parquet/live_ingestor/_/{窗口}/`;根目录只能在 UI Data Lab → Providers → Parquet 改(**没有环境变量**,`parquet_schema.py:176-184`)。
- **覆盖策略**:WS 订阅流动性 Top `ws_max_tokens=5000` + 活跃成交;全宇宙(~4 万 token)每 600s REST 全量 L2 基线(`recording_feed.py:50`)。
- **谁在跑**:专门的 **recording worker plane**(`workers/host.py:330-357`)。**GUI 启动器会拉起全部 8 个 plane**(`gui.py:241-282`,trading/recording/reconciliation 恒开)——你本机用 GUI 跑的话录制面是在的。
- **另录两路事件总线 parquet**:`crypto.update.dispatch`(**含 `oracle_history` 的完整 crypto 行**,`market_runtime.py:2054-2210`)和 `polymarket.catalog.snapshot`。加密策略回测的 oracle 数据就靠这路。
- **回测怎么读**:`MarketDataView` 不扫目录,查 Postgres `provider_datasets` 目录表(`services/marketdata/coverage.py:96-120`)——所以「文件在但目录表没登记」= 回测看不见。

## 3. 必须立刻改的三件事(默认配置撑不起回测)

1. **留存 7 天 → 拉长**。book parquet 默认 `book_retention_days=7 / book_max_bytes=40GB`(`book_parquet_sink.py:59-60`),crypto 总线 topic 默认 `7 天 / 8GB`(`market_runtime.py:2148-2149`)。walk-forward 默认 6 折,7 天数据几乎不够切。改法:`PUT /api/dataset/recorder/config` 把 `book_retention_days` 提到 ≥30(注意磁盘:全宇宙 L2 一天可能几个 GB,盯 `book_max_bytes`);UI Data Lab → Topics 把 `crypto.update.dispatch` 的 retention_days/max_bytes 同步拉高。**先拉留存再攒数据**——被裁掉的窗口不可恢复。
2. **settlement 库定时回填**。`market_settlements` **没有任何常驻进程写入**(只有导入、回测时在线回填、手动脚本三条路)。加个 cron:每天跑 `python -m scripts.backfill_market_settlements --days 30`(`backend/scripts/backfill_market_settlements.py`),否则严格离线回测(`settle_resolution_allow_network=False`)没有结算真值。
3. **别指望 `trade_signals` 存历史**。该表是 **UNLOGGED**(Postgres 非正常关机直接清空,迁移 `202606160002` 自述"ephemeral")且终态信号 **24 小时就被清理**(`workers/host.py:665-686`)。回测的持久基底是 parquet + 事件总线,信号重放只对最近一天可靠——所以回测跑 `discover_from_history=True`(默认)让策略在录制数据上重新检测即可,不依赖旧信号。

## 4. 坑清单(会静默毁数据/骗你的)

- **`backend/data/cache/parquet_retention.json` 是死配置**:全仓库无任何代码读它,改它无效。真实留存在 `recorder_config_json` + `topic_catalog`。
- **磁盘守卫**:空闲 <10GB 时录制**静默丢弃** flush 并紧急裁窗口(`book_parquet_sink.py:277-294,490-514`)。给数据盘留足空间,否则录着录着就断档。
- **docker-compose 部署 = 不录制**:compose 只定义了 trading/news/discovery 三个 worker,**没有 recording/detection/jobs plane**,且容器内 parquet 路径不在挂载卷里(容器重建即丢)。你是 GUI 启动器跑的就没这问题;如果哪天迁 compose,必须补 plane 服务 + parquet volume。
- **oracle_history 只存在于「录制窗口」**:从外部导入的 parquet 走 gap-fill 投影(`services/marketdata/projection.py`),投影行**没有 oracle_history 字段**——加密策略只能在自己录的窗口上高保真回测。这就是为什么 §3.1 必须先把 crypto topic 留存拉高。
- **`opportunity_history` 默认 30 天清理**(`maintenance.py:73`,可调 `cleanup_opportunity_history_days`)。

## 5. 数据攒到什么程度能跑什么

- **保真度**:回测引擎按快照密度评级,≥30 snaps/token/小时 = high,≥6 = medium(`strategy_backtester.py:4133-4136`)。600s REST 基线兜底 = 恰好 medium;WS 覆盖的 top5000 token 轻松 high。
- **加密高频批**:5m/15m 周期一天就有几百个循环,**录 3–7 天即可开始有统计意义的回测**;先跑 `run_execution_backtest` 基线,再 sweep。
- **walk-forward**:`n_folds=6, train_ratio=0.5` 默认——想切 6 折×每折有意义,**至少 30 天**,所以 §3.1 的留存必须先改。
- **`run_parameter_sweep` 注意**:它走 scanner 缓存 + Polymarket 价格历史 REST(24h 回看,`strategy_backtester.py:29-31`),需要**在线**且只回看一天——适合快扫,严谨结论以 execution backtest / walk-forward 为准。
